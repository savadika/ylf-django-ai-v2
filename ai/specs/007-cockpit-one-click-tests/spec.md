# 驾驶舱一键核心回归测试

## 背景与问题

驾驶舱目前只展示上一次质量报告。开发者想确认用户、角色、菜单、部门等既有功能是否仍然正常时，
仍需回到终端手动选择测试命令。页面上的状态因此可能与当前代码实时状态不一致。

## 目标

- 驾驶舱提供清晰可见的“一键测试核心功能”按钮。
- 点击后运行 91 项 Django 核心业务测试和 56 项前端测试，并在页面展示进度、结果、数量和耗时。
- 测试失败时在页面展示对应套件的输出，方便定位。
- 只有通过 `quality.py serve` 打开时才允许启动测试；直接打开静态 HTML 时给出明确提示。
- 防止浏览器跨站请求或非本机客户端触发测试进程。

## 非目标

- 不在生产环境暴露测试入口。
- 不运行前端 lint、部署检查或修改业务数据；测试仍使用内存 SQLite 和 locmem cache。
- 不引入新的 Web 框架、数据库、外部前端依赖或常驻任务队列。

## 用户故事

- 作为项目维护者，我希望在驾驶舱点击一次就能确认核心功能是否正常，从而不必记忆命令。
- 作为开发者，我希望看到失败套件和原始输出，从而快速定位回归。
- 作为安全负责人，我希望本地测试入口不能被外部网站任意触发。

## 验收标准

- [x] AC-001 驾驶舱显示“一键测试核心功能”按钮，运行时禁用按钮并展示进行中状态。
  验证：`test_cockpit.py` 与浏览器检查。
- [x] AC-002 点击后依次执行后端核心 API 和前端单元测试，返回两项状态、用例数、耗时及原始失败输出。
  验证：`test_test_runner.py` 与真实 HTTP 请求。
- [x] AC-003 只有本机、带专用请求头的 `POST /api/core-tests/run` 可以启动测试；非法请求被拒绝。
  验证：`test_test_server.py` 的 HTTP 接口测试。
- [x] AC-004 页面在 file 模式或接口错误时保持可用，并显示可操作的中文错误提示。
  验证：`test_cockpit.py` 的脚本文本检查与浏览器手工检查。
- [x] AC-005 通过 `quality.py serve` 打开后，一次点击可得到后端和前端测试均通过的结果。
  验证：浏览器实际点击与 `verification.md` 的响应证据。

## 约束与风险

- 测试会占用本机 CPU 约 10-20 秒，接口需要防止并发启动多个测试进程。
- 服务只绑定本机时按钮可用；通过远程访问驾驶舱时不开放测试执行。
- 页面继续是单文件静态产物，只允许内联 JavaScript，不请求外部脚本、样式、字体或图片。
- 测试进程必须有超时限制，异常必须转为页面可显示的失败结果。
