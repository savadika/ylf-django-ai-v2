# UniDjango 编码约定

这份文档记录代码本身看不出来的约束。框架入口、脚本名称和目录结构以仓库文件为准，这里不重复维护。

## 共同原则

- 一个改动只解决一个可验证的问题；行为改动必须有规格或任务编号。
- 公共接口优先保持稳定；需要破坏兼容性时，在规格中写迁移方案和回滚方案。
- 输入在边界校验，异常在边界转换为统一错误；内部代码传递明确的数据结构。
- 注释解释“为什么”和约束，不复述代码“做了什么”。
- 测试名称描述业务结果，并使用 Arrange / Act / Assert 组织用例。
- 源码、文档和配置统一使用 UTF-8；提交前保持 LF 换行。

## 后端（Django / DRF）

### 分层与依赖

- `urls.py` 只负责路由，`views.py` 编排请求和事务，`serializers.py` 负责输入输出校验，
  `models.py` 表达持久化约束。跨模块能力放在 `utils/`。
- ViewSet 统一继承 `utils.viewsets` 中的基类，保证响应信封、复杂查询和权限行为一致。
- 成功响应使用 `Ok`，业务错误使用 `ApiException` 或 `utils.exceptions` 中的响应类型。
  响应结构保持 `{code, message, data}`。
- 新增 action 时必须同时配置权限映射；未配置 action 按 fail-closed 处理。
- 涉及多表写入使用 `transaction.atomic()`；删除被保护外键前先在同一事务内清理关联。
- 查询列表接口要评估 N+1，按需使用 `select_related` 或 `prefetch_related`。

### 模型与迁移

- 模型字段必须声明 `verbose_name`；业务表使用 `BaseModel`、`TimestampMixin`、
  `RemarkMixin`、`StatusMixin` 等现有抽象。
- 唯一性、外键删除策略和状态约束优先放在模型或数据库层；只有数据库无法表达的规则才放在序列化器。
- 迁移文件随模型改动一起提交，禁止修改已经在共享环境执行过的迁移。
- 权限标识沿用 `system:<resource>:<action>`，例如 `system:user:list`。

### 安全与兼容

- 密码只以哈希形式存储，日志、过滤器、响应和测试快照中都不能出现明文密码或 token。
- JWT、缓存、媒体 URL 和客户端 IP 统一复用 `user/` 与 `utils/` 中的实现。
- 外部输入按最小字段接收，批量更新要处理重复 ID 和不存在 ID。
- 新接口至少覆盖成功、校验失败、未认证和权限不足中的相关分支。

## 前端（Vue 2 / Element UI）

- 组件使用 PascalCase 文件名，页面组件放在 `src/views/<domain>/index.vue`，可复用组件放在
  `src/components/`。
- HTTP 请求集中在 `src/api/`，页面组件不直接拼接后端地址。
- 共享状态只进入 Vuex 模块；组件局部状态留在组件内部。
- 权限按钮使用 `v-permission`，权限码与后端保持一致。
- 用户可见文案使用中文；日志和异常保留足够上下文，不输出敏感数据。
- 新组件优先使用 props 和事件通信，避免通过父组件实例直接修改子组件状态。
- 前端测试放在 `business/frontend/tests/unit/`，至少覆盖核心计算、权限判断和关键交互。

## 测试写法

- 后端测试放在对应应用的 `tests.py` 或 `tests/` 包中；纯逻辑使用 `SimpleTestCase`，
  数据库行为使用 `TestCase`。
- 外部 Redis、日志线程和网络调用要替换为内存实现或 mock，测试不依赖本机服务状态。
- 每个回归测试在名称或注释中引用规格验收项，例如 `test_locked_after_failures_ac_003`。
- 前端测试以行为和输出为主，避免断言实现细节。
- 覆盖率是趋势闸门，不是替代用例设计的指标；新增高风险分支时同步提高策略阈值。

## 评审清单

- 规格、实现、测试和迁移是否指向同一个行为？
- 是否新增了未配置权限的 action、未索引的高频查询或未处理的事务边界？
- 是否泄露密码、token、内部路径或异常堆栈给客户端？
- 失败路径是否返回稳定的错误码和响应信封？
- 是否运行了与改动范围匹配的验证，并在 `verification.md` 记录证据？
